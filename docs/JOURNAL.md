# Collective journal reflections — 2026-11-15

This is the current journal contract for **both the website and the native iPhone journal**.
The user's direction supersedes the original optional-MUSE, on-device-only summary requirements
in the brief, execution plan, hackathon brief and historical handoff. No camera or alert contract changes.

## Experience and data flow

- Every new journal save automatically requests MUSE. The save button and nearby disclosure say
  that dated text goes through the configured CrewSafety website to Meta. There is no MUSE opt-out
  toggle or local sentiment/summary panel. Photo comparison remains a separate explicit opt-in.
- Save the entry first. Provider/network/configuration/rate-limit failure leaves it saved with a
  pending reflection and a retry button; it never substitutes a local or fabricated AI reflection.
  Old entries are not silently uploaded on launch. Retry is an explicit request under the same disclosure.
- Context is the selected entry plus at most **11 earlier entries within the preceding 14 days**.
  Include positive and negative wording chronologically; do not select only similar or negative notes.
  Identical text on different entries is retained. Future entries are excluded. Earlier text is
  excerpted at 1,500 characters and marked as excerpted; the current text may contain 10,000 characters.
- MUSE reviews every save. **Entries 1–2** receive a brief acknowledgement and question, with an
  empty suggestions array and a visible progress message. **3 or more entries within 14 days** unlock
  collective reflection and 1–3 practical suggestions. Three is a product threshold, not a clinical
  threshold; the three entries need not all be negative or on different days. Clients also hide
  suggestions on older saved reflections covering fewer than three entries. Explicit immediate
  danger still prompts human-support wording in the message, regardless of count.
- MUSE may tentatively acknowledge repeated **self-described feelings**, suggest 1–3 manageable
  actions, and ask a gentle question. It must not infer depression or another disorder, assign a
  mental-health risk score, prescribe treatment, or claim NASA/clinical validation. Sparse entries
  do not establish that a feeling persisted continuously. Positive changes and ambiguity matter.
- The VADER-derived wording heuristic runs only in `web/journal-analysis.mjs`. Its labels and scores
  are transient internal context for MUSE. Neither those fields nor provider reasoning are returned
  or stored. The response parser allowlists only public feedback; the prompt also prohibits exposing
  internal analysis in prose. This is prompt guidance, not a clinically validated content filter.
- Public reflections contain `message`, `suggestions`, `question`, dated context coverage, model and
  generation time. Context includes `minimumEntries:3`. They are stored beside entries and shown to the writer. Existing native summary
  fields remain readable for file compatibility but are no longer generated or displayed.

## Optional cat-video break

After a successful reflection covering at least three entries, both clients show **A little cat
break** with two fixed Cole & Marmalade YouTube links: [Meet Marmalade](https://www.youtube.com/watch?v=UnJCiJD1mig)
and [The First Time Cole and Marmalade Met](https://www.youtube.com/watch?v=XswFdWL7HM0).
The same section appears in the astronaut demo. It is optional entertainment, not treatment or a
claim of benefit, and does not replace the MUSE message or practical suggestions. No video autoplay,
embedded player, thumbnails or requests to YouTube occur until the user opens a link. URLs are
fixed in the clients, never generated by MUSE or populated with journal text. Web links suppress
the referrer and open a separate tab. Native links use the system URL opener.

## Astronaut presentation demo

Website and native iPhone Journal have **Run astronaut demo**. Three clearly fictional dated entries
show an illustrated astronaut becoming homesick, lonely and very low. After the third, the client
requests real MUSE feedback using `POST /api/journal/demo` with only `{consent:true}`. The server owns
the fixed preset text; it never authenticates an account, reads/writes the database, accepts supplied
history or updates Mission progress. The response includes `demo:true` and the same public reflection
fields as the normal journal. Internal analysis remains server-only.

The demo opens separately from the editor and history. It works for guests and signed-in users,
respects reduced-motion settings, can be closed during generation, and shows a retry on failure.
The website also offers **Show all three entries** to skip the presentation. Closing and reopening
replays it; demo feedback is not persisted. Internet and configured MUSE credentials are required;
there is no canned AI result. The illustration is not camera-based emotion inference.

## Isolation and storage

Account requests send `{entryId, consent:true}`. The server authenticates the cookie, selects that
user's history, and persists only public feedback. Client-supplied account history is rejected.
Deleting an entry clears the account's saved reflections; an in-flight response cannot retain deleted
context. Accounts/admins never gain another user's journal through this endpoint.

Guest browsers and native iPhones send `{entry:{body,date}, history:[{body,date}], consent:true}`.
Guest data and returned feedback persist in localStorage. Native data and feedback persist in the
protected `journal.json`; context is limited to the same `crewMemberID`, and requests carry no web
cookies or crew identifiers. Native and account journals remain separate stores, not synchronized.
Neither journals nor reflection responses are service-worker cached. Device text still reaches
CrewSafety and Meta during reflection; local persistence does not mean local-only processing.

Account text and public feedback are stored in D1/SQLite without application-level encryption.
Device history and internal sentiment are not persisted by the reflection endpoint. Provider-side
retention follows Meta's service settings; this implementation does not establish zero retention.

## API, configuration and rollout

`POST /api/journal/analyze` requires JSON, disclosed consent and the server's exact Origin. Both
clients set that origin. It returns only structured public feedback, never raw provider output.
It uses the existing `META_API_KEY` and optional `META_MODEL` server variables. Native requests use
Settings → Website connection → Advanced: website address, defaulting to CrewSafety Connected; HTTPS is required except
for localhost development. No provider credential is embedded in either client.

Apply `web/drizzle/0008_journal_reflections.sql` to hosted D1 before deploying the Worker. Its tag is
registered in Drizzle's migration journal. Local Node startup applies it automatically. Run on
Node 22.13+, then `npm test` and `npm run build` from `web/`; syntax-check the generated Worker too.
Deploy the updated API before distributing the new iPhone build. The old endpoint accepts a different
payload and will leave new clients' reflections pending. The FastAPI crew-sync service does not implement
this journal route; use the Node/Worker website URL, not the old FastAPI dashboard address.

The bulk move action migrates existing browser entries; it does not automatically resubmit every
historical note to Meta. Imported entries show pending feedback until explicitly retried. Mission's
photo-only check-in also does not silently send historical journal text.

## Advice references and verification

The prompt's low-risk coping options were checked against
[NHS Every Mind Matters: low mood](https://www.nhs.uk/every-mind-matters/mental-health-issues/low-mood/)
and [WHO: Doing What Matters in Times of Stress](https://www.who.int/publications/i/item/9789240003927/).
They support general coping suggestions, not diagnosis or clinical evaluation of this prototype.

Web tests cover consent/input limits, mixed chronological history, repeated wording, account isolation,
long-entry excerpts, hidden-field removal, malformed/incomplete/provider-failed responses, persistence,
deletion during generation, the 1/2/3 threshold, urgent-support wording below the threshold, and
fictional demo isolation from account storage. Native tests cover same-crew history bounds, network payload/privacy,
provider failure with saved text, disk failure, persistence and deletion while generation is pending.
See [PASSDOWN](PASSDOWN.md) for the current run results and deployment status.
